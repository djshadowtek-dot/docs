Cloud Logging collects, indexes, and stores logs from your Google Infrastructure resources and applications automatically, giving you a centralized place to search and analyze operational data. Logs begin flowing from most Google Cloud services the moment you create resources — no manual configuration required. For your own applications, you can write structured log entries via the CLI, client libraries, or the Logging API. This guide covers the log types available, how to query them effectively, and how to route logs to external systems for long-term retention or analysis.

## Log Types

Google Infrastructure generates several categories of logs automatically. Understanding the distinction helps you find the right log quickly during troubleshooting and ensures you have the right audit logs enabled for compliance.

| Log Type | Description | Enabled by Default |
|---|---|---|
| **Admin Activity** | Records API calls that create, modify, or delete resources — for example, creating a VM or updating an IAM policy. | ✅ Always on |
| **Data Access** | Records API calls that read resource configurations or metadata, and calls that create, modify, or read user-provided data. | ❌ Must be enabled per service |
| **System Event** | Records Google system events such as live migration of a VM instance. Generated by Google, not user actions. | ✅ Always on |
| **Policy Denied** | Records when a request is denied by a VPC Service Controls perimeter or an organization policy constraint. | ✅ Always on |
| **Application Logs** | Logs written by your own code using the Cloud Logging API, client libraries, or the `gcloud logging write` command. | User-configured |

<Note>
  Data Access logs are retained for **30 days** by default. Admin Activity logs are retained for **400 days**. If your compliance requirements mandate longer retention periods, configure a log sink to export logs to Cloud Storage or BigQuery before the default retention window expires. You cannot recover logs that have passed the retention window without a sink in place.
</Note>

## Viewing Logs in Log Explorer

The **Log Explorer** in the Cloud Console provides an interactive interface for querying and inspecting log entries. You can filter logs by resource type, log name, severity level, and time range, or write custom queries using the Logging Query Language (LQL).

To open Log Explorer, navigate to **Logging → Log Explorer** in the Cloud Console.

### Basic Filters

Use the filter bar to narrow logs by common attributes:

- **Resource type**: `Compute Engine VM Instance`, `Cloud SQL Database`, `GKE Container`, etc.
- **Log name**: `cloudaudit.googleapis.com/activity`, `run.googleapis.com/requests`, etc.
- **Severity**: `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`
- **Time range**: use the time picker to focus on the window relevant to an incident

### Logging Query Language (LQL)

LQL gives you precise control over log queries. Write queries in the query editor to filter on any log field, including nested JSON fields in structured log payloads.

```
-- Find all ERROR logs from a specific Cloud Run service in the last hour
resource.type="cloud_run_revision"
resource.labels.service_name="my-api"
severity=ERROR
timestamp>="2024-11-01T10:00:00Z"

-- Find IAM policy changes made by a specific user
logName="projects/my-project/logs/cloudaudit.googleapis.com%2Factivity"
protoPayload.authenticationInfo.principalEmail="alice@example.com"
protoPayload.methodName:"SetIamPolicy"
```

## Writing Custom Application Logs

Write log entries from your own code or scripts using the `gcloud` CLI. This is useful for scripted workflows, deployment pipelines, or quick debugging sessions.

```bash
gcloud logging write my-log "Hello from Google Infrastructure" --severity=INFO
```

Write a structured JSON log entry to make entries easier to query and parse downstream:

```bash
gcloud logging write my-log \
  '{"message": "Deployment complete", "version": "2.3.1", "environment": "production"}' \
  --severity=INFO \
  --payload-type=json
```

For production applications, use the Cloud Logging client libraries which handle batching, retries, and structured payload formatting automatically.

<Tip>
  Enable **Data Access audit logs** for services that store sensitive data — such as Cloud Storage, BigQuery, and Cloud SQL — so you have a full record of who accessed which data and when. Data Access logs are disabled by default because they can generate high log volumes. Enable them selectively for your most sensitive resources to balance auditability with cost. Navigate to **IAM & Admin → Audit Logs** in the Cloud Console to configure Data Access log settings per service.
</Tip>

## Log-Based Metrics

Log-based metrics let you extract quantitative signals from your log stream and feed them into Cloud Monitoring for dashboards and alerting. For example, you can count the number of HTTP 500 errors per minute from your application logs and alert when the rate exceeds a threshold.

```bash
gcloud logging metrics create http-500-errors \
  --description="Count of HTTP 500 errors from the API service" \
  --log-filter='resource.type="cloud_run_revision" AND httpRequest.status=500'
```

Once created, the metric appears in Cloud Monitoring under the `logging.googleapis.com/user/` metric namespace and behaves like any other metric — you can chart it, set alert conditions on it, and include it in dashboards.

## Log Sinks: Exporting Logs

Log sinks route copies of your log entries to an external destination — Cloud Storage, BigQuery, or Pub/Sub — as they arrive. Use sinks to satisfy long-term retention requirements, power analytics pipelines, or feed logs into a SIEM.

```bash
gcloud logging sinks create my-sink \
  storage.googleapis.com/my-log-bucket \
  --log-filter='severity>=ERROR'
```

The `--log-filter` parameter uses the same LQL syntax as Log Explorer, giving you precise control over which entries are exported. After creating the sink, grant the sink's service account write access to the destination bucket:

```bash
# Get the sink's writer service account
gcloud logging sinks describe my-sink --format="value(writerIdentity)"

# Grant Storage Object Creator on the destination bucket
gsutil iam ch serviceAccount:WRITER_IDENTITY:objectCreator gs://my-log-bucket
```
